根因：`scripts/fetch-registry.js` 第 236 行补用药时执行 `UPDATE ... SET medicines=?, verify_source=?, verify_date=?`，只更新用药、不动 verified，却顺手写入了“核实日期”，71 条待核实记录由此带上日期。

处理：人工逐条复核这 71 条；确认无误的置 verified=1，不准备上线的清空 verify_date（source 可保留作溯源）。

~~~sql
-- 待复核清单（71 条）
SELECT id, name, category, verify_source, verify_date
FROM diseases
WHERE verified = 0 AND TRIM(COALESCE(verify_date, '')) <> ''
ORDER BY id;

-- 复核通过后按 id 上线（示例）
-- UPDATE diseases SET verified = 1 WHERE id IN (48, 50, 51);

-- 不准备上线的：清掉“核实日期”，避免继续误导
-- UPDATE diseases SET verify_date = NULL
-- WHERE verified = 0 AND TRIM(COALESCE(verify_date, '')) <> '';
~~~

### P3 · 约束与流程（防复发）

**8）数据库约束**（先完成 P0/P1 清理，否则 CHECK 会因存量数据失败）

~~~sql
-- 已核实必须有来源和日期
ALTER TABLE diseases
  ADD CONSTRAINT chk_verified_meta CHECK (
    verified = 0 OR (
      TRIM(COALESCE(verify_source, '')) <> ''
      AND TRIM(COALESCE(verify_date, '')) <> ''
    )
  );

-- JSON 字段必须是合法 JSON（NULL 允许）
ALTER TABLE diseases
  ADD CONSTRAINT chk_disease_json CHECK (
    (medicines   IS NULL OR JSON_VALID(medicines))
    AND (suggestions IS NULL OR JSON_VALID(suggestions))
    AND (prevention  IS NULL OR JSON_VALID(prevention))
  );
~~~

**9）代码侧流程（建议改代码，本次未改）**

- `agriculture-backend/routes/admin.js` 的“核实”接口只校验 `verify_source`，不校验也不写入 `verify_date`；建议在 `verified=1` 时同时写入 `verify_date = CURDATE()`，并拒绝空来源（现有逻辑已拒绝，保留）。
- `agriculture-backend/scripts/fetch-registry.js` 第 236 行补用药时不应写 `verify_date`（当前 71 条未核实记录带日期即由此产生）；如需记录抓取时间，应另加 `enriched_at` 字段。
- 后台新增/编辑病害时对 medicines/suggestions/prevention 做“JSON.parse 且为数组”校验，避免坏 JSON 入库。
- 详情页对 `JSON_LENGTH=0` 的板块隐藏，避免已核实记录出现空标题。
